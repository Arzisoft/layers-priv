# Module 2: Composer and Chat: Directing AI Through the Interface — Exam

> Exam for **Module 2: Composer and Chat: Directing AI Through the Interface** (The Mastery) — 25 questions, pass mark 80%. Correct answers are marked ✅ (read from each question's own post record; no quiz attempt was started to get them).

### Q1. A builder wants to understand how an unfamiliar function works before deciding anything. Which mode fits, and why?

- **A.** The terminal, because function behavior can only be understood by executing it and reading the raw output it produces at runtime
- **B.** Composer, because explanations are more accurate when the AI is simultaneously being allowed to modify the code it is explaining to you live
- **C.** Chat, because it answers questions and explains code without touching files, making it the zero-risk mode for understanding and planning  ✅
- **D.** Neither mode, because understanding code requires reading it yourself line by line before any AI involvement is appropriate at all

> **Answer:** C

### Q2. A builder needs a new settings page added across four files. Which mode does this module say handles this, and what does it produce?

- **A.** Chat, which outputs the code as text for the builder to paste into each of the four files manually after reviewing every snippet
- **B.** Composer or Agent mode, which plans and then applies real changes across the affected files and presents them as reviewable diffs  ✅
- **C.** The extensions panel, which installs a page generator that scaffolds settings pages without involving the AI conversation at all
- **D.** The terminal, which runs a scaffold command that creates the page, since multi-file creation is a command-line operation by nature

> **Answer:** B

### Q3. A builder types 'make the login better' and gets changes they did not want. Per this module, what was wrong with the instruction?

- **A.** It was sent in the wrong mode, since improvement requests belong in Chat and only literal feature additions belong in Composer
- **B.** It was a wish, not a specification: it named no elements, no current behavior, and no desired behavior for the model to build toward  ✅
- **C.** It was too long, since effective instructions stay under five words and any additional detail dilutes the model's attention on the goal
- **D.** It lacked an apology, since politeness tokens measurably improve output quality and blunt instructions produce careless changes

> **Answer:** B

### Q4. This module says every message travels with more than your words. What does Cursor package with your instruction?

- **A.** Your account history and billing tier, since the model calibrates response quality to exactly how long you have been a paying customer
- **B.** Only the exact text you typed, since Cursor deliberately strips all context to keep the model's attention on your words alone
- **C.** A screenshot of your screen, since the model reads the interface visually to understand what you are looking at while typing
- **D.** Relevant context: the active file, files you reference, selected code, and results from the codebase index, alongside your words  ✅

> **Answer:** D

### Q5. A builder is about to direct a change with several moving parts. Which habit does this module say prevents most runaway edits?

- **A.** Type the instruction in all capital letters, since emphasis signals importance and importance signals the model to work carefully
- **B.** Split the work across five separate conversations, since fresh context windows prevent the model from attempting too much at once
- **C.** Direct the plan first: have the AI list the steps and files it will touch, approve or adjust the plan, then tell it to proceed  ✅
- **D.** Disable file writing before sending, since a read-only session forces the AI to describe changes rather than making them at all

> **Answer:** C

### Q6. A builder receives a multi-file diff from Composer. What does this module say they must do before the changes land?

- **A.** Review the diffs, accepting what is right and rejecting or redirecting what is not, since blind-accepting is how mystery bugs enter  ✅
- **B.** Run the formatter on every file first, since formatting normalizes the diff and makes acceptance safe without further reading
- **C.** Accept everything immediately, since Composer output is pre-validated and review only delays landing changes that already passed
- **D.** Forward the diff to another builder, since self-review is unreliable and only a second person can approve multi-file changes

> **Answer:** A

### Q7. A builder's first output from a directed build is close but not right. How does this module frame what should happen next?

- **A.** Iterate inside the same conversation: first output is a draft, and two or three directed passes of review and correction is the normal rhythm  ✅
- **B.** Accept the output as-is, since first drafts represent the model's best understanding and corrections rarely improve on them
- **C.** Start a new conversation and rephrase from scratch, since imperfect output means the current context is contaminated beyond saving
- **D.** Switch to a different model immediately, since a model that misses on the first attempt will miss the same way on every following attempt

> **Answer:** A

### Q8. A builder wants only the date formatting changed in one dashboard file and nothing else. Which instruction pattern does this module teach?

- **A.** A general improvement request, since the AI infers your true scope from the conversation history without explicit boundaries stated
- **B.** A scoped correction naming the boundary: only change the date formatting in the dashboard, and do not touch anything else in the file  ✅
- **C.** A two-part request asking for the change plus any other improvements the AI notices, since bundling maximizes the value per message
- **D.** A silent selection, since highlighting the code communicates scope by itself and written boundaries are fully redundant with the selection

> **Answer:** B

### Q9. A builder asks how mode names like Chat, Ask, Composer, and Agent relate across Cursor versions. What does this module say?

- **A.** The names refer to different models rather than modes, so switching between them is really switching AI providers underneath
- **B.** Each name is a separate product with separate billing, and builders choose one at signup that cannot be changed afterward
- **C.** Names shift between versions, but that split persists: identify modes by what they do, one discusses and one changes files  ✅
- **D.** Older names remain functional forever, so builders can ignore renames entirely and use whichever historical label they learned

> **Answer:** C

### Q10. A builder wrote an instruction: outcome, then constraints ('match existing styles, validate on client, success state without reload'). What is this pattern called in this module, and why does it work?

- **A.** Prompt stuffing, which works by exhausting the model's attention so it defaults to the safest and most conventional implementation
- **B.** Context anchoring, which works by repeating the same requirement three times so the model cannot lose it during generation
- **C.** Defensive prompting, which works by anticipating model errors and pre-blocking each one before the model can commit to making it
- **D.** Outcome plus constraints, which works because it gives the model a specification to build toward rather than a wish to interpret  ✅

> **Answer:** D

### Q11. A builder cannot decide between exploring an idea and building it. Per this module's decision framework, how do the modes divide that work?

- **A.** Build first in Composer, then explore what you built in Chat afterward, since real code is the only honest basis for exploration
- **B.** Explore in Chat until you settle on an approach, then build the settled choice in Composer, each mode doing the job it is for  ✅
- **C.** Both happen in Composer, since exploring and building are the same activity once the AI can modify files during the discussion
- **D.** Both happen in Chat, since Composer is reserved for emergencies and routine building belongs in the discussion mode by default

> **Answer:** B

### Q12. A builder gives a correction: 'The error message shows above the field; move it below, styled like the other form hints.' What makes this correction effective per this module?

- **A.** Its politeness, since corrections framed as gentle suggestions consistently outperform corrections framed as direct statements
- **B.** Its brevity, since corrections under ten words are processed with higher priority than longer and more detailed instructions
- **C.** It names what was wrong and what right looks like, giving the model the current behavior and the desired behavior to move between  ✅
- **D.** Its timing, since corrections sent immediately after output carry more weight than corrections sent after testing the changes

> **Answer:** C

### Q13. A builder wanted an explanation but sent their question to Composer and got file edits. What does this module call this mistake?

- **A.** Using Composer mode for questions, which is why you ask in Chat when you do not want changes to be made to anything on disk  ✅
- **B.** A model failure, since a correctly functioning AI should recognize questions and refuse to edit regardless of the mode chosen
- **C.** A version bug, since current Cursor releases automatically reroute questions to the discussion mode without builder action
- **D.** An indexing error, since questions only trigger edits when the codebase index has drifted out of sync with the project files

> **Answer:** A

### Q14. A builder gets a useful answer in Chat, then manually copies code from the chat into three files by hand. What does this module say about this workflow?

- **A.** It is the recommended safe path, since manual pasting forces the review that Composer's automatic application would let you skip
- **B.** It is required for multi-file work, since Composer is limited to single files and anything larger must flow through Chat and manual pasting
- **C.** It misuses the modes: when you want changes applied, Composer applies them for you, and hand-pasting around Chat is its job done badly  ✅
- **D.** It is faster than Composer for small changes, so this module recommends it whenever fewer than five files are involved in the change

> **Answer:** C

### Q15. A builder is deciding whether to hand a large well-specified task list to Cursor or Claude Code. What division does this module suggest?

- **A.** Claude Code for anything involving files, Cursor for conversations only, since the tools divide strictly by whether disk changes occur
- **B.** Cursor for all of it, since Claude Code duplicates Cursor's features and running both tools on one project causes state conflicts
- **C.** Whichever is open at the moment, since the two tools are interchangeable and switching costs outweigh any difference between them
- **D.** Claude Code for the long autonomous run, then Cursor to review and refine results visually, since each tool serves its half well  ✅

> **Answer:** D

### Q16. This module says instruction discipline transfers between Cursor and Claude Code. What stays the same across both tools?

- **A.** The keyboard shortcuts, since both tools standardize on identical bindings so muscle memory transfers without any relearning
- **B.** The interface layout, since Claude Code renders the same four zones in the terminal that Cursor renders in its window
- **C.** The outcome-plus-constraints directing pattern, since both tools take the same specification and reward the same discipline  ✅
- **D.** The pricing structure, since both tools bill by accepted diff and the cost discipline is what actually transfers between them

> **Answer:** C

### Q17. A builder wants to know what Chat can safely be used for at any time. What property makes Chat the zero-risk mode?

- **A.** Nothing changes on disk when you use it, so questions, explanations, and approach discussions carry no risk to your files  ✅
- **B.** It runs on a separate safety-tuned model, so its answers are more cautious than the model that powers the file-editing mode
- **C.** It automatically backs up the project first, so even though it edits files, every change can be recovered from the backup
- **D.** It requires confirmation before responding, so the extra click prevents accidental questions from reaching the model at all

> **Answer:** A

### Q18. Mid-build, the AI produced something wrong and the builder is tempted to open a fresh conversation. What does this module say they lose by restarting?

- **A.** Their remaining message quota, since restarted conversations bill at a higher rate to discourage abandoning active sessions
- **B.** Nothing at all, since context carries over automatically between conversations and restarting is purely a cosmetic reset
- **C.** Their place in the queue, since new conversations wait behind existing ones and restarting adds real latency to every following message
- **D.** All the context built in the conversation, which a focused correction inside the same conversation would have kept working for them  ✅

> **Answer:** D

### Q19. A builder wants the AI to answer questions grounded in their actual project rather than generically. Which Chat pattern does this module model?

- **A.** Reference specific files or code in the question, like asking where a discount check belongs in the checkout flow, and why there  ✅
- **B.** Ask in the shortest form possible, since brevity forces the model to fill gaps from the codebase rather than from general knowledge
- **C.** Ask the question twice in a row, since repetition signals importance and importance triggers the model to consult the project
- **D.** Preface the question with the project name, since naming the project activates the index for the remainder of the conversation

> **Answer:** A

### Q20. A builder sends a multi-step instruction and the AI makes ten changes, three wrong. Untangling takes an hour. What would the plan-first habit have cost instead?

- **A.** Nothing at all, since plan approval happens instantly and reviewing a plan takes no measurable time compared to reviewing changes
- **B.** A full extra session, since plans require their own conversation and the overhead only pays off on projects above a certain size
- **C.** The build's momentum, since stopping to plan breaks flow and this module treats the hour of untangling as the cheaper of the two costs
- **D.** A minute of reading the step list and adjusting it, which is why the module treats plan-first as the habit that prevents runaway edits  ✅

> **Answer:** D

### Q21. A builder notices small context indicators on their message showing what is attached. Why does this module say to glance at them?

- **A.** So you can bill clients accurately, since attached context is metered separately and the indicators show the charge per message
- **B.** So you know what the model can see, since directing precisely depends on knowing what context traveled with your instruction  ✅
- **C.** So you can screenshot them for support, since context indicators are diagnostic codes the Cursor team uses to debug sessions
- **D.** So you can disable them, since context attachment slows responses and expert builders send bare instructions without any context

### Q22. A builder expects perfect output in one shot, gets a near-miss, and concludes Cursor is overhyped. What does this module say about that expectation?

- **A.** It is correct, and near-misses mean the builder should file feedback and wait for a stronger model before continuing to build
- **B.** It sets builders up for frustration: builders who expect two or three directed passes ship, while one-shot expectations stall projects  ✅
- **C.** It is correct for small projects only, since one-shot perfection is the norm below a thousand lines and iteration is a big-project tax
- **D.** It reveals a configuration error, since properly configured setups produce shippable output on the first attempt in most cases

### Q23. After approving a plan and receiving changes, the builder runs the result and something is broken. Per this module's loop, what happens next?

- **A.** Feed what is broken back into the conversation and iterate, since direct, review, run, correct is the working rhythm of building  ✅
- **B.** The conversation ends, since a broken result signals context corruption and continuing in the same thread compounds the errors
- **C.** The plan is invalidated, so the builder discards all applied changes and starts the planning phase over with a corrected description
- **D.** The builder fixes it by hand, since the AI's involvement ends at delivery and post-run corrections are the builder's manual work

> **Answer:** A

### Q24. A builder asks when the plan-first pattern is worth invoking. What threshold does this module give?

- **A.** Anything with more than a couple of moving parts, since multi-step work is where unplanned edits run away from the builder  ✅
- **B.** Only when a client is paying, since personal projects tolerate runaway edits and planning discipline is a billable-work habit
- **C.** Every single message, since even one-line questions benefit from a plan step and skipping it anywhere breaks the discipline
- **D.** Only above twenty files, since planning overhead exceeds its value on anything smaller than a major architectural change

> **Answer:** A

### Q25. Looking across this whole module, what is the governing principle of directing AI through Composer and Chat?

- **A.** Minimize your instruction length in every mode, since the model performs best when given maximum freedom to interpret your intent broadly
- **B.** Prefer whichever mode responds faster, since latency is the real constraint on building and mode semantics matter less than throughput
- **C.** Keep all work in a single mode to avoid context loss, since switching between Chat and Composer resets what the model knows about you
- **D.** Match the mode to the intent and direct with specs: discuss in Chat, change in Composer, plan first on multi-step, and review every diff  ✅

> **Answer:** D
