# Module 7: Ship: Live API Product — Exam

> Exam for **Module 7: Ship: Live API Product** (The Mastery) — 25 questions, pass mark 80%. Correct answers are marked ✅ (read from each question's own post record; no quiz attempt was started to get them).

### Q1. This capstone says shipping an API product differs from shipping a feature. What happens on launch day that makes the difference?

- **A.** The infrastructure bill arrives, so the team must immediately optimize costs before the first month of production traffic overwhelms them
- **B.** Strangers begin building businesses on your endpoints, so everything you deferred becomes load-bearing the moment the API goes live  ✅
- **C.** The documentation is frozen, so any endpoint that was left undocumented can no longer be changed once the launch has been announced
- **D.** The version number resets, so the API restarts at version one and all prior internal testing versions are discarded at general availability

> **Answer:** B

### Q2. This capstone lists the launch checklist. Which set of items matches what it says must actually be in place, not merely planned?

- **A.** A pricing page, a blog post, a demo video, and a launch tweet, since the checklist is fundamentally about marketing the API's debut widely
- **B.** A funded runway, a hiring plan, a board deck, and a growth model, since launching an API is primarily a business-planning milestone
- **C.** Documentation complete, rate limits configured, billing wired, monitoring active, and the status page live, each tracing back to a module  ✅
- **D.** A trademark, a privacy policy, a cookie banner, and a data-processing agreement, since launch readiness is mainly a legal-compliance exercise

> **Answer:** C

### Q3. This capstone recommends most API products launch to a beta before general availability. What is a beta?

- **A.** A free tier that never expires, since a beta is simply the permanent no-cost plan that lets any developer try the API without paying
- **B.** A controlled group of early-access developers who tolerate rough edges and give feedback in exchange for getting in early on the API  ✅
- **C.** A load test, since a beta exists chiefly to generate enough synthetic traffic to prove the infrastructure can survive the real launch
- **D.** A marketing campaign, since a beta is the pre-launch publicity phase that builds an audience before the product is actually available

> **Answer:** B

### Q4. This capstone says the beta has a special power that general availability does not. What is it?

- **A.** Higher rate limits, since beta developers are granted unlimited access as compensation for tolerating the API's early rough edges
- **B.** Lower pricing, since beta is the only phase where the API can be offered below cost to attract developers before revenue matters
- **C.** No monitoring burden, since a beta API is exempt from uptime commitments and can go down freely while the team iterates on it
- **D.** You can still change things since beta developers have agreed to absorb breaking changes in exchange for early access to the API  ✅

> **Answer:** D

### Q5. This capstone says the beta's breaking-change contract must be explicit. What goes wrong if it is left implicit?

- **A.** The metering drifts, since an implicit contract leaves the billing system unsure whether to charge beta developers for their usage
- **B.** The beta lasts too long, since without a stated contract the team has no signal for when the API is finally ready to reach availability
- **C.** A developer who thinks they are on a stable API and gets broken feels betrayed, while one who knows it is a beta expects the change  ✅
- **D.** The docs fall out of sync, since an unstated breaking-change policy removes the trigger that would prompt updating the reference material

> **Answer:** C

### Q6. This capstone says general availability is a promise of stability requiring specific commitments. Which set does it name?

- **A.** Terms of service, an SLA commitment, and support channels, since GA is the point at which those promises become real and binding  ✅
- **B.** A larger server fleet, a caching layer, and a load balancer, since GA is fundamentally an infrastructure-scaling milestone for the API
- **C.** A new major version, a fresh OpenAPI spec, and a rewritten quickstart, since GA marks a clean restart of the API's public contract
- **D.** A marketing budget, a sales team, and a partner program, since GA is the point at which the company begins investing in growth

> **Answer:** A

### Q7. This capstone says a launch can fail even with great functionality. What does it identify as the cause of such a failure?

- **A.** The product around the API is incomplete, such as missing docs, unconfigured limits, or no status page, even though the API itself works  ✅
- **B.** The functionality is too advanced, since developers reject an API whose capabilities exceed what they are ready to integrate at launch
- **C.** The price is too low, since a launch priced below the competition signals low quality and drives serious developers to alternatives
- **D.** The version number is too high, since launching at a high version implies instability that makes developers wait for it to settle down

> **Answer:** A

### Q8. This capstone says the beta is where you find the gaps real developers hit before those gaps meet your entire market. What kind of gaps does it name?

- **A.** The latency spikes, the failover bugs, and the region outages, since a beta exists chiefly to stress the reliability of the infrastructure
- **B.** The pricing objections, the contract redlines, and the procurement delays, since beta is primarily about testing the sales motion early
- **C.** The security holes, the exposed keys, and the injection flaws, since a beta functions mainly as a penetration test before launch
- **D.** The confusing errors, the missing example, and the endpoint that does not behave as documented, surfaced by real developer use in beta  ✅

> **Answer:** D

### Q9. This capstone says you do not declare GA until you can honor the commitments. Why is that discipline important?

- **A.** GA triggers the marketing spend, so declaring it early wastes the launch budget before the product is discoverable enough to convert
- **B.** GA is the point at which those promises become real so declaring it before you can honor terms, SLA, and support breaks them on day one  ✅
- **C.** GA resets the version, so declaring it prematurely forces an awkward re-versioning once the real stability commitments are finally ready
- **D.** GA locks the pricing, so declaring it before the model is final leaves the API unable to adjust its rates as costs become clearer later

> **Answer:** B

### Q10. This capstone says growth for an API product runs through developer channels. Which three does it name?

- **A.** Paid search, display ads, and retargeting, since an API is a product like any other and grows through conventional performance marketing
- **B.** Developer marketing, partner integrations, and marketplace listings, since developers are the buyers and advocates who drive API growth  ✅
- **C.** Outbound sales, cold email, and trade shows, since enterprise API deals are closed the same way any other enterprise software is sold
- **D.** Discounts, referral bonuses, and loyalty points, since API growth is driven by the same incentive mechanics as consumer subscriptions

> **Answer:** B

### Q11. This capstone says the through-line of API growth is that developers are the buyers and advocates. What does growth therefore mean?

- **A.** Making developers successful and visible, since an API that developers love gets recommended, and recommendation is the strongest growth  ✅
- **B.** Undercutting competitors on price, since developers are cost-sensitive buyers who choose whichever API charges the least per call made
- **C.** Adding the most features, since developers are drawn to whichever API has the longest capability list regardless of its usability
- **D.** Locking developers in early, since the way to grow is to make switching so painful that no integrated developer can ever leave you

> **Answer:** A

### Q12. This capstone describes switching costs as cutting both ways. What does it say you must do to earn the lock-in they create?

- **A.** Raise prices steadily, since integrated developers cannot easily leave and the way to profit from lock-in is to charge them more over time
- **B.** Stop shipping changes, since once developers are integrated the safest way to keep them is to freeze the API and never risk breaking it
- **C.** Remove the competition's integrations, since lock-in is earned by making it technically impossible to run your API alongside a rival's
- **D.** Be reliable and respectful of their investment, since you earn lock-in that way or lose it the first time you break them carelessly  ✅

> **Answer:** D

### Q13. This capstone says each launch-checklist item traces back to a module. What does that tracing imply about a gap in any one item?

- **A.** A gap is a version issue, since an incomplete checklist simply means the API should launch at a lower version number than planned
- **B.** A gap is acceptable, since the checklist is aspirational and an API can launch successfully with several of its items still outstanding
- **C.** A gap is a marketing problem, since the checklist items are promotional deliverables rather than functional requirements for the API
- **D.** A gap is a launch defect, since each unchecked item represents a whole module's worth of work left undone that the launch depends on  ✅

> **Answer:** D

### Q14. This capstone says a beta program should be designed deliberately. Which three design decisions does it name?

- **A.** The price, the discount, and the trial length, since a beta is fundamentally a pricing experiment run before the real launch begins
- **B.** The region, the language, and the protocol, since a beta is chiefly about testing the API across the technical environments it will serve
- **C.** Who gets in, how feedback flows back, and that breaking changes are acceptable, since the expectation must be set before developers join  ✅
- **D.** The logo, the tagline, and the landing page, since a beta is primarily a branding exercise that shapes how the launch will be perceived

> **Answer:** C

### Q15. This capstone says an API product is durable because switching costs are real. What does it warn is the flip side of that durability?

- **A.** You lose the lock-in the first time you break developers carelessly, since the same switching cost that holds them turns to resentment  ✅
- **B.** You cannot raise prices, since real switching costs mean developers watch your pricing closely and leave the moment rates increase at all
- **C.** You cannot add features, since integrated developers resist any change and durability comes only from freezing the API permanently
- **D.** You cannot version, since switching costs make developers refuse migrations and the API is trapped forever on its very first release

> **Answer:** A

### Q16. This capstone says GA means a developer can build a business on your API with reasonable confidence. What three properties does it say GA guarantees?

- **A.** It will be free, unlimited, and unversioned, since GA removes the beta's constraints and opens the API fully to every developer at no cost
- **B.** It will be fast, cached, and globally distributed, since GA is the point at which the API's performance infrastructure is fully built out
- **C.** It will be there, versioned responsibly, and supported, since GA is the commitment that makes the API safe to depend on for a business  ✅
- **D.** It will be documented, marketed, and listed, since GA is the moment the API becomes discoverable across every developer channel at once

> **Answer:** C

### Q17. This capstone says a launch that goes out missing docs, limits, or a status page fails for a specific reason. What is that reason?

- **A.** The product around the API is incomplete, since the API can be functionally excellent while the surrounding product is not yet finished  ✅
- **B.** The API is too slow, since missing a status page means the team never measured latency and shipped an unoptimized service to market
- **C.** The API is insecure, since launching without configured limits leaves every endpoint exposed to the abuse that scanners would have caught
- **D.** The API is mispriced, since an incomplete launch signals the team did not understand its costs and set rates it cannot sustain profitably

> **Answer:** A

### Q18. This capstone says the beta window is used to get the design right while you still can. What must happen at GA regarding that design?

- **A.** You freeze all development, since GA means the API can never change again and every future need must be met by a separate new product
- **B.** You reset the design, since GA is a clean restart where the beta's decisions are discarded and the API is rebuilt from scratch again
- **C.** You commit to stability, since after GA breaking changes require versioning and migration rather than the free changes beta allowed  ✅
- **D.** You raise the price, since GA is when the value proven during the free beta is finally converted into the revenue the API will earn

> **Answer:** C

### Q19. This capstone pulls the whole course together. Which description matches how it summarizes a complete API product?

- **A.** A single endpoint, one pricing plan, a static PDF reference, a flat monthly bill, and a best-effort uptime, since simplicity is what developers want
- **B.** A fast server, a big feature list, a low price, a broad free tier, and a large marketing budget, since those are what make almost any API succeed
- **C.** A design developers navigate, an access layer that tiers into revenue, docs that win adoption, metering that bills accurately, and monitoring that keeps the promise  ✅
- **D.** A proprietary protocol, a closed ecosystem, a locked client library, an exclusive partner list, and a restrictive license, since control drives durability

> **Answer:** C

### Q20. This capstone says recommendation is the cheapest and strongest growth an API product has. What produces that recommendation?

- **A.** A viral marketing stunt, since a memorable campaign is what gets an API discussed and shared far more than the quality of the product does
- **B.** A generous referral bonus, since paying developers a cash reward for each signup they bring is what reliably drives word-of-mouth growth
- **C.** An aggressive discount, since the lowest price is what developers share with peers and cheapness is the message that spreads fastest
- **D.** An API that developers love since a product developers succeed with gets recommended, which is stronger than any paid acquisition channel  ✅

> **Answer:** D

### Q21. This capstone says you should not declare GA until you can honor your SLA. What does that imply about the SLA you commit to at GA?

- **A.** It must be one the architecture can actually honor, since the GA SLA is the external, binding version of the availability promise from monitoring  ✅
- **B.** It must exceed every competitor's, since the GA SLA is chiefly a marketing number and a bolder promise wins more enterprise deals at launch
- **C.** It must be left unspecified, since committing to any concrete availability figure at GA exposes the provider to penalties it cannot predict
- **D.** It must apply only to paid tiers, since free-tier developers have no standing to expect any uptime guarantee from the API at all

> **Answer:** A

### Q22. This capstone frames the API product as a long-term relationship with a community of developers. What does it say every module in the course was?

- **A.** A separate revenue stream, since each module describes an independent product the team can sell alongside the core API for extra income
- **B.** A way of keeping that relationship worth staying in, since design, access, docs, metering, versioning, and monitoring all serve the same end  ✅
- **C.** A one-time setup task, since each module is configured once at launch and then never revisited across the life of the API product
- **D.** A defensive measure against competitors, since each module exists chiefly to make the API harder for a rival to copy or displace

### Q23. This capstone names partner integrations and marketplace listings as growth channels alongside developer marketing. What do partner integrations specifically bring?

- **A.** Other products that build you in and bring their users, since a partner that integrates your API exposes you to its own audience  ✅
- **B.** Cheaper hosting, since partners share their infrastructure and let the API run at a lower cost than it could achieve on its own
- **C.** A higher SLA, since partnering with larger platforms lets the API inherit their uptime guarantees and promise more availability
- **D.** Fewer support tickets, since partners handle first-line support for their own users and shield the API team from direct contact

> **Answer:** A

### Q24. This capstone says a beta should include feedback loops. Why are feedback loops a deliberate part of beta design rather than an afterthought?

- **A.** They lower the price, since structured feedback from beta developers is what justifies discounting the API before it reaches availability
- **B.** They are how you learn the gaps real developers hit, since the beta's purpose is to surface confusing errors and missing examples early  ✅
- **C.** They replace monitoring, since developer feedback during beta surfaces outages more reliably than instrumenting the API to measure them
- **D.** They satisfy compliance, since documented feedback channels are a legal prerequisite before an API may be offered to external developers

> **Answer:** B

### Q25. Looking across everything in this capstone, what is the governing principle for launching a live API product?

- **A.** Launch as early as possible, because being first to market matters more than completeness and the missing pieces can be added under real load
- **B.** Launch to the largest possible audience at once, because a public general-availability launch generates more attention than a limited beta ever could
- **C.** Launch quietly and let functionality speak, because a superior API needs no beta, no status page, and no developer marketing to grow on its own
- **D.** Assemble the whole product, prove it in beta, commit at GA, and grow through developers, because an API is a long-term relationship, not a feature  ✅
