# Module 7: Production Memory Systems and Debugging — Exam

> Exam for **Module 7: Production Memory Systems and Debugging** (The Frontier) — 25 questions, pass mark 80%. Correct answers are marked ✅ (read from each question's own post record; no quiz attempt was started to get them).

### Q1. A memory system works perfectly on the builder's laptop. What changes when it becomes a production deployment target?

- **A.** It gains migrations, environment separation, backups, and access rules: it is infrastructure  ✅
- **B.** It moves onto a heavier database tier, since laptop-grade Postgres cannot hold real user load
- **C.** It gets rewritten in a compiled language, since prototypes rarely survive real traffic
- **D.** It adds a caching layer, since production reads arrive faster than any store can serve

> **Answer:** A

### Q2. In what order does a production boot sequence bring an agent online?

- **A.** Identity, standing instructions, current state, and only then accept user input  ✅
- **B.** Current state, then user input, then identity, with instructions loaded lazily as needed
- **C.** User input first, then whatever memories the first query happens to retrieve
- **D.** Standing instructions, user input, then state fetched in the background async

> **Answer:** A

### Q3. Bertha, the production agent pattern, is described as never surprised by her own life. What makes that true?

- **A.** Her model was fine-tuned on her history, so her past is part of her weights
- **B.** She boots from persistent state every session, waking into a current picture  ✅
- **C.** Her sessions never end, so there is no restart at which surprise could occur
- **D.** Her users brief her at session start, supplying whatever context she lacks

> **Answer:** B

### Q4. A reviewer asks how the boot sequence should be treated in engineering terms. What does production-grade mean here?

- **A.** Versioned, token-budgeted, and tested like an API contract, kept in the repo  ✅
- **B.** Encrypted, compressed, and rotated on the same schedule as the access keys
- **C.** Regenerated by the model each morning, so startup content stays adaptive
- **D.** Owned by operations rather than the builder, since startup is a runtime issue

> **Answer:** A

### Q5. A builder wants the taxonomy of retrieval failures. Which four stages cover almost every memory bug?

- **A.** Corrupt embedding, cold cache, wrong index, and overloaded database connection
- **B.** Bad prompt, wrong model, missing tool, and a context window that is set too small
- **C.** User error, agent error, platform error, and the unclassifiable residual error
- **D.** Never written, not retrieved, ranked too low to admit, or admitted but stale  ✅

> **Answer:** D

### Q6. A fact is wrong in production. The write-path log shows no record of it ever being captured at any session close. Which stage failed?

- **A.** Admission: the scorer excluded it so often that the log rotation dropped it
- **B.** Retrieval: the query never matched, so the log has nothing against which to match
- **C.** Staleness: the record aged out and the log purged its history alongside it
- **D.** The write: the memory was never captured, so no downstream stage ever had it  ✅

> **Answer:** D

### Q7. The memory exists in the store, correct and current, but the candidate list in the read log never contains it. Which stage is broken?

- **A.** The write path: correct storage with wrong metadata still counts as a write bug
- **B.** Admission: the scoring function is discarding it before candidates are formed
- **C.** Retrieval: the query or filters never surface it into the candidate set at all  ✅
- **D.** The boot sequence: memories missing at startup cannot appear as candidates

> **Answer:** C

### Q8. A rescheduled meeting was written and appears among retrieval candidates, yet the agent still quotes the old time. The read log shows the old memory scoring higher. Stage?

- **A.** Not retrieved: candidacy without admission means retrieval never truly happened
- **B.** Ranked too low to admit: the fact lost the scoring contest to its predecessor  ✅
- **C.** Never written: candidate lists can contain phantom entries from stale indexes
- **D.** Stale admission: the wrong memory entered the window after its facts expired

> **Answer:** B

### Q9. An agent confidently cites a fact that was true in March and false since June. The June update was never linked to the March record. Which fix closes this class of bug?

- **A.** A larger candidate pool, so both versions surface and the model can choose
- **B.** A shorter half-life, so all old memories fade before they can mislead anyone
- **C.** A supersede rule: updates archive their predecessors instead of coexisting  ✅
- **D.** A boot sequence check that re-verifies every fact against the live calendar

> **Answer:** C

### Q10. A builder wants a memory quality dashboard. Which metric set matches the recommendation?

- **A.** Uptime, error rate, deploy frequency, and mean time to recovery per incident
- **B.** Retrieval hit rate, staleness of admitted memory, corrections, and cost per session  ✅
- **C.** Row count, table size, index depth, and vacuum frequency on the memory store
- **D.** Model latency, tokens per response, refusal rate, and weekly user satisfaction scores

> **Answer:** B

### Q11. User corrections per week just doubled, though no one has complained. How should a builder read this signal?

- **A.** As a leading indicator: memory quality is slipping before users start leaving  ✅
- **B.** As noise: correction counts vary naturally with usage and mean little week to week
- **C.** As success: corrections mean users are engaged enough to teach the agent
- **D.** As a UI problem: too-easy correction buttons inflate the weekly numbers

> **Answer:** A

### Q12. For every memory write, the log records what was written, by whom, from which session, and why. What does this buy when a fact goes wrong?

- **A.** Automatic rollback: the log doubles as an undo journal for every bad write
- **B.** Legal cover: provenance records satisfy client audits of stored information
- **C.** Fault location: extraction, storage, and retrieval bugs become distinguishable  ✅
- **D.** Faster writes: structured logging lets the database batch its inserts more efficiently

> **Answer:** C

### Q13. What belongs in the read-path log for each retrieval, so admission decisions can be reconstructed later?

- **A.** Only failed queries, since successful retrievals need no later explanation
- **B.** The final answer text, since downstream output is what users actually dispute
- **C.** The full window contents per turn, so any session replays deterministically
- **D.** The query, the candidates, their scores, and which memories were admitted  ✅

> **Answer:** D

### Q14. An agent states a fictional fact about a real client. Investigation finds a test session wrote it. What discipline was missing?

- **A.** Environment separation: test sessions must never write production memories  ✅
- **B.** Prompt hygiene: test instructions should label fictional data as fictional
- **C.** Importance scoring: test writes should enter with weights too low to admit
- **D.** Session expiry: test data should decay within hours instead of persisting

> **Answer:** A

### Q15. An agent's morning behavior changed and nobody knows why. The startup contents were edited last week without record. Which mistake is this?

- **A.** An unversioned boot sequence: silent startup changes shift behavior invisibly  ✅
- **B.** A monitoring gap: behavior change alerts should page whichever team owns the agent
- **C.** A model regression: providers change weights and mornings expose it first
- **D.** Memory drift: accumulated writes gradually reshape any agent's disposition

> **Answer:** A

### Q16. A team has nightly backups of their memory store but has never once restored one. What should they call this state?

- **A.** Standard practice: restores are rare events and rehearsing them wastes cycles
- **B.** Acceptable if backups are checksummed, since integrity implies restorability
- **C.** A compliance gap, closed by documenting the restore procedure in the runbook
- **D.** A hope, not a plan: memory is irreplaceable state and restore must be rehearsed  ✅

> **Answer:** D

### Q17. An agent forgot a client detail, and the builder spends three days tuning retrieval scoring. The write log would have shown the detail was never captured. What went wrong in the debugging?

- **A.** Nothing: scoring is the likeliest culprit, so starting there was rational
- **B.** The builder tuned in production, where scoring changes affect live users
- **C.** Three days is normal: memory bugs tend to resist any systematic investigation
- **D.** Stages out of order: check whether it was written before touching ranking  ✅

> **Answer:** D

### Q18. A production schema change is needed on the memories table. What is the disciplined path?

- **A.** Edit the live table in a low-traffic window, with a teammate watching the change
- **B.** Fork the production project, apply changes there, and swap the connection string
- **C.** A migration promoted through dev first; live tables are never edited by hand  ✅
- **D.** Queue the change until quarterly maintenance, batching schema work for safety

> **Answer:** C

### Q19. Hit rate has slid three points over six weeks. Nothing is down and no errors fire. What should the monitoring be built to do here?

- **A.** Nothing: alerting belongs to outages, and gradual metrics recover on their own
- **B.** Page immediately on any metric movement, since silence hides every failure
- **C.** Alert on drift, not just downtime: slow degradation is the failure mode here  ✅
- **D.** Rebaseline weekly, so gradual slides become the new normal automatically

> **Answer:** C

### Q20. Which description matches the AI Chief of Staff pattern this course builds toward?

- **A.** A scheduling assistant that books meetings and sends reminders from static calendar rules
- **B.** An agent booting into your calendar, projects, and open loops, maintaining its own store  ✅
- **C.** A dashboard summarizing all your agents' activity into one single morning email digest
- **D.** A wrapper that routes your requests to whichever model suits each of the tasks

> **Answer:** B

### Q21. How do this course's subsystems relate to the Chief of Staff build?

- **A.** Loosely: the Chief of Staff pattern replaces most of them with managed services
- **B.** Directly: memory types, retrieval, maintenance, and boot are its working organs  ✅
- **C.** Optionally: only retrieval matters once the calendar integration is in place
- **D.** Sequentially: each subsystem is retired as the next one comes online in turn

> **Answer:** B

### Q22. A production memory bug went from report to root cause in eleven minutes. What most plausibly made that speed possible?

- **A.** A senior engineer who had personally seen this exact failure pattern before
- **B.** A small store: fast diagnosis is a benefit of keeping the memory counts low
- **C.** Both paths were logged: writes and reads answered each taxonomy stage in turn  ✅
- **D.** A staging replay: the bug reproduced immediately on the development stack

> **Answer:** C

### Q23. Why does the boot sequence carry a hard token cap, like 2,000 tokens?

- **A.** Provider APIs reject startup payloads above certain fixed limits set per account tier
- **B.** Startup loads spend from the same window the session needs; the cap protects it  ✅
- **C.** Caps force summaries, and summarized state is more reliable than raw state
- **D.** Billing alarms trigger on large fixed costs, and caps keep mornings quiet

> **Answer:** B

### Q24. A team debates skipping observability because 'a simple retrieval_log table feels too basic.' What is the right response?

- **A.** Basic beats blind: a plain log table outperforms no observability by far  ✅
- **B.** Agreed: wait for a proper telemetry stack before logging anything at all
- **C.** Split the difference: log only errors until a real pipeline gets budgeted
- **D.** Skip tables entirely: provider dashboards already show every model call

> **Answer:** A

### Q25. Across deployment, monitoring, and debugging, what defines a production-ready memory system?

- **A.** One that has reached complete feature coverage across every one of its memory subsystems
- **B.** One that runs on dedicated infrastructure with a full on-call rotation behind it
- **C.** One that no longer needs maintenance because its store has reached a steady state
- **D.** One that is deployed, monitored, debuggable, and boots the agent current every session  ✅

> **Answer:** D
