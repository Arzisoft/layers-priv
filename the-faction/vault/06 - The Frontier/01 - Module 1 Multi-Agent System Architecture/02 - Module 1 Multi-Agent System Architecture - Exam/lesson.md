# Module 1: Multi-Agent System Architecture — Exam

> Exam for **Module 1: Multi-Agent System Architecture** (The Frontier) — 25 questions, pass mark 80%. Correct answers are marked ✅ (read from each question's own post record; no quiz attempt was started to get them).

### Q1. When does a multi-agent architecture genuinely beat a single capable agent?

- **A.** Always, since more agents means more intelligence applied to any problem of any size at all
- **B.** When work benefits from parallelism, specialization, or isolation that one context can't hold well  ✅
- **C.** Never, since the coordination overhead always exceeds the benefit of splitting up any given task
- **D.** Only for image generation tasks, since text work is inherently single-agent by its nature

> **Answer:** B

### Q2. In an orchestrator pattern, what is the orchestrator agent's job?

- **A.** To perform every subtask itself while the worker agents observe and learn directly from its outputs
- **B.** To store the system's long-term memory, acting as the database for all the worker agents
- **C.** To compete against the workers on identical tasks, keeping quality high through rivalry
- **D.** To decompose the goal, assign work to specialized agents, and integrate results into one outcome  ✅

> **Answer:** D

### Q3. What must a clean handoff between two agents include?

- **A.** The task, the relevant context, the expected output format, and any constraints that apply  ✅
- **B.** The complete history of every prior task the sending agent has ever performed for anyone
- **C.** A financial transaction record, since agent handoffs require metered billing between the two of them
- **D.** Nothing; agents share knowledge automatically once they run on the same provider's models

> **Answer:** A

### Q4. Why is shared context one of the hardest problems in multi-agent systems?

- **A.** Because context is copyrighted per agent, so sharing it between different models violates licensing terms
- **B.** Because agents refuse to accept context generated by other agents without human sign-off first
- **C.** Because each agent sees only what it's given, so state must be deliberately passed or stored in reach  ✅
- **D.** Because context can only move between agents at fixed times of day set by the model providers

> **Answer:** C

### Q5. Why direct specialized agents instead of one generalist doing all three?

- **A.** Focused roles with tight instructions each do their job better, and the reviewer isn't grading its own work  ✅
- **B.** Specialized agents cost less per token, since providers discount narrowly scoped requests significantly
- **C.** Generalist agents are being phased out by the major providers, making specialization the only real option
- **D.** One agent legally cannot both build and review, since separation of duties is a regulated requirement

> **Answer:** A

### Q6. One agent in your pipeline produces garbage output. What does good architecture do with that failure?

- **A.** Lets it flow through, since downstream agents naturally recognize and repair any upstream garbage
- **B.** Contains it: validation between stages catches bad output before it poisons the rest of the pipeline  ✅
- **C.** Restarts the entire system from zero, since any single failure invalidates all completed work
- **D.** Ignores it permanently, since occasional garbage is statistically insignificant across runs

> **Answer:** B

### Q7. When should agents run in parallel rather than as a sequential chain?

- **A.** Never, since parallel agents always produce conflicting outputs that cannot ever be merged
- **B.** Always, since parallelism is strictly faster and speed is the only architectural concern
- **C.** Only overnight, when provider rate limits loosen enough to allow concurrent requests
- **D.** When subtasks are independent of each other, so no agent is waiting on another's output  ✅

> **Answer:** D

### Q8. Multiple agents are updating the same project state and overwriting each other. What is the architectural fix?

- **A.** More agents, adding a dedicated referee to argue with any agent that writes conflicting data entries
- **B.** Slower agents, adding deliberate delays so writes naturally spread out across the timeline
- **C.** A single source of truth with controlled writes, so state changes flow through one governed path  ✅
- **D.** No shared state at all, accepting that each agent's private view will permanently diverge

> **Answer:** C

### Q9. Where does the human AI Directed Engineer sit in a well-designed multi-agent system?

- **A.** Defining goals, standards, and checkpoints, directing the system rather than every message in it  ✅
- **B.** Inside every agent-to-agent exchange, manually relaying each message between all the participants
- **C.** Nowhere; mature multi-agent systems are defined by the total absence of human involvement
- **D.** Only at the very end, discovering what the system decided after everything has already run

> **Answer:** A

### Q10. How many agents should a system have?

- **A.** As many as budget allows, since capability scales linearly with the number of agents deployed
- **B.** Always exactly three, since architecture research converged on three as the universal optimum
- **C.** One per employee replaced, since agent headcount should mirror the human org chart directly
- **D.** The fewest that cleanly cover the needed roles; every added agent adds coordination cost  ✅

> **Answer:** D

### Q11. Three agents each produced their piece of a deliverable. What step do inexperienced builders most often skip?

- **A.** Publishing each piece separately, since assembled deliverables hide the individual agent work done
- **B.** Deliberate integration: merging, reconciling conflicts, and verifying the pieces work as one whole  ✅
- **C.** Congratulating the agents, since positive reinforcement measurably improves future outputs
- **D.** Archiving the pieces unmerged, since integration is the client's responsibility after handoff

> **Answer:** B

### Q12. Why do orchestrated systems pass summaries between agents instead of full transcripts?

- **A.** Full transcripts are prohibited from crossing between different agent sessions by providers
- **B.** Summaries are more truthful than transcripts, since compression removes hallucinated content
- **C.** Context is finite and costly; passing only what the next agent needs keeps each stage sharp  ✅
- **D.** Transcripts can only be read by the agent that produced them, making sharing impossible

> **Answer:** C

### Q13. What should you design first when directing AI to build a multi-agent system?

- **A.** The workflow itself: the stages, decisions, and quality gates the work must move through  ✅
- **B.** The agent names and personas, since identity design determines system performance most
- **C.** The billing dashboard, since cost visibility is the foundation every architecture rests on
- **D.** The failure announcement templates, since communicating breakage is the hardest problem

> **Answer:** A

### Q14. Between agent stages, when should plain automation handle the connection instead of another agent?

- **A.** Never, since inserting non-AI steps into an agent pipeline breaks the whole system's intelligence
- **B.** Whenever the step is mechanical, moving, formatting, routing, where reliability beats reasoning  ✅
- **C.** Only when budgets are exhausted, since automation is the degraded fallback for agent work
- **D.** Whenever clients are watching, since automation demonstrations impress better than agents

> **Answer:** B

### Q15. You can't tell which stage of your multi-agent pipeline degrades quality. What is missing?

- **A.** More powerful models at every stage, which remove the need to locate specific weaknesses
- **B.** A larger orchestrator, since degradation is always caused by insufficient central capacity
- **C.** Agent enthusiasm, since output quality tracks the motivational framing in system prompts
- **D.** Observability: logging each stage's inputs and outputs so you can see where quality drops  ✅

> **Answer:** D

### Q16. Agent B keeps misunderstanding what Agent A hands off. Where do you look first?

- **A.** The handoff itself: is the context complete, the format defined, and the expectation explicit?  ✅
- **B.** Agent B's attitude, since downstream agents develop resistance to upstream instructions
- **C.** The provider's status page, since misunderstandings between agents indicate live service outages
- **D.** The time of day, since inter-agent comprehension measurably degrades outside business hours

> **Answer:** A

### Q17. What role does an external memory store play in a long-running multi-agent system?

- **A.** It replaces the agents entirely once enough history accumulates for lookup-based responses
- **B.** It exists for compliance only, since agents never actually read from external memory stores
- **C.** It holds durable state agents can read and write, surviving context resets across sessions  ✅
- **D.** It slows the system deliberately, adding friction that prevents agents from acting too fast

> **Answer:** C

### Q18. An agent hits a situation outside its instructions. What should the architecture make it do?

- **A.** Improvise confidently, since agents that ask questions erode stakeholder trust in the whole system
- **B.** Escalate: flag the situation to the orchestrator or human instead of guessing past its mandate  ✅
- **C.** Halt the entire company's systems, since any uncertainty invalidates all concurrent work
- **D.** Delete its context and retry from nothing, since fresh starts resolve most edge conditions

> **Answer:** B

### Q19. How do you test a multi-agent pipeline meaningfully?

- **A.** Test only the final output, since internal stages are implementation details without meaning
- **B.** Never test it, since agent systems are non-deterministic and therefore untestable by nature
- **C.** Test only the orchestrator, since worker correctness follows from correct task assignment
- **D.** Both levels: each stage against its own contract, and the whole pipeline against end goals  ✅

> **Answer:** D

### Q20. Adding a review agent to every stage tripled quality slightly and quintupled cost and latency. What does this teach?

- **A.** Cost is irrelevant in architecture, since quality improvements justify any resource multiple
- **B.** Review agents are a scam, since checking work is something buyers of AI should never fund
- **C.** Architecture is trade-offs; place expensive checks where errors are costly, not everywhere  ✅
- **D.** Latency and quality are unrelated, so the slowdown must come from a provider-side issue

> **Answer:** C

### Q21. What is the most common failure mode when builders first adopt multi-agent architecture?

- **A.** Overengineering: building agent swarms for tasks a single well-directed agent handles better  ✅
- **B.** Underspending: refusing to deploy enough agents for even the simplest possible workloads around
- **C.** Naming collisions: two agents sharing a name, which silently corrupts provider routing
- **D.** Timezone drift: distributed agents falling out of sync across international deployments

> **Answer:** A

### Q22. Why define structured output formats for every agent in a pipeline?

- **A.** Providers charge less for structured output, making format definitions a pure cost play
- **B.** Structure prevents agents from being creative, which is the whole goal of professional systems
- **C.** Unstructured output is illegal to pass between automated systems in regulated industries
- **D.** Downstream stages can rely on predictable shape, so parsing and validation stay dependable  ✅

> **Answer:** D

### Q23. Why should the agent that reviews work be separate from the agent that produced it?

- **A.** Provider terms require fully separate billing accounts for production and for review workloads
- **B.** A fresh context evaluates against the standard instead of defending its own prior choices  ✅
- **C.** Review agents run on special models that production agents are not permitted to access
- **D.** It doubles the invoice line items, which makes the engagement look more substantial

> **Answer:** B

### Q24. What is the disciplined path to a multi-agent system?

- **A.** Design the full swarm on paper first and build all agents simultaneously for coherence
- **B.** Copy a famous company's published architecture exactly, since proven designs transfer directly
- **C.** Start with one agent, find where it genuinely strains, and split only at those proven seams  ✅
- **D.** Start with twenty agents and delete downward, since subtraction is easier than addition

> **Answer:** C

### Q25. Which principle should guide every multi-agent architecture decision?

- **A.** Coordination is the product: clear roles, clean handoffs, and verified integration beat agent count  ✅
- **B.** More is more: agent count is the single metric that separates serious systems from experiments
- **C.** Set and forget: well-designed systems should never require observation once deployed
- **D.** Novelty first: architectures should showcase the newest patterns regardless of the task

> **Answer:** A
